# Create a Lite Wearable project and check it in the Previewer

## Setup on the Windows PC

- DevEco Studio **6.1.1** (build 243.24978.46.36.611280) at `E:\Programs\Huawei\DevEco Studio`. It was downloaded from https://developer.huawei.com/consumer/en/download/, which needs a Huawei ID login. winget's `Huawei.DevEco` only has 3.1.0.
- The bundled SDK is HarmonyOS 6.1.1(24) at `E:\Programs\Huawei\DevEco Studio\sdk\default`. It includes the Lite Wearable previewer (`openharmony/previewer/liteWearable`), so no extra SDK download was needed. DevEco also brings its own Node and ohpm under `tools/`.
- User data lives in `%LOCALAPPDATA%\Huawei\` and `%APPDATA%\Huawei\DevEcoStudio6.1`.

## Creating the project

File > New > Create Project > Application > **[Lite]Empty Ability** (the template with a watch icon). It is JS, FA model, `deviceType: liteWearable`. The template accepts compatible SDKs 4.0.0(10) to 6.1.1(24).

`Counter/` was created with:

| Field | Value |
|---|---|
| Project name | Counter |
| Bundle name | `com.hectorreto.counter` (the AppGallery Connect app must use the same package name) |
| Save location | `huawei-watch\Counter` |
| Compatible SDK | **5.0.0(12)**, the lowest common value that GT 6 projects use; the confirmed GT 6 project used 5.0.5(17), which this DevEco does not list |
| Target SDK | 6.1.1(24), set by the wizard in `build-profile.json5` |

The first sync shows "Project sync failed" while ohpm installs packages; it retries on its own and finishes in about 30 s. Ignore the banner if the Sync tab ends with exit code 0.

Driving the wizard with computer use: DevEco Studio is granted at **full** tier (typing works), because it is not recognised as an IDE.

## The app

`entry/src/main/js/MainAbility/pages/index/` is one page with three views, switched with `if` on `view`: the cookie, the shop and the achievements. Changing `view` is enough, so no `@system.router` page is needed and the production timer keeps running in the other views.

**Cookie view:** a `stack` laid out with `left`/`top`. At the bottom is the cookie, a full-screen 466 px `div` with `onclick="increment"` and the edge swipe (`onswipe="edgeSwipe"`, see **Gestures**). Over it are the curved count (below) and the "+N" texts (below). The overlays are kept small because taps on them do not reach the cookie. There are no buttons on the big cookie; the edge swipe opens the menu (below). In the Previewer a swipe does not also count as a tap. Each tap:

- adds `tapPower` (1 + one per "Tastier taps");
- shows a white "+N" with a dark outline (plain white text was hard to read on the cookie) at a random spot below the curved count, which stays in place and fades over 1 s. Lite does not allow binding `class` to data (build error "class selector does not support data binding"), so each "+N" is two `if` groups and a tap swaps which one exists; each starts its animation when it is created. Lite `text` has no `text-shadow` or stroke (the lite component map gives `text` no such style), so a group is a `stack` of four dark copies of the text, 2 px off diagonally, under the white one, each with a fixed `left`/`top` from its own class (`plus-outline-1`..`4`). Before this it was white text on a black rounded pill. Greying out unaffordable shop rows uses the same trick. Binding `style` does compile: `style="left: {{ plusX0 }}px; top: {{ plusY0 }}px;"` becomes a `dynamicStyle` in the built page. The bound position is on a 144x44 `plus-row` `stack` holding the two groups, as the earlier fixed row was; a first try that put it straight on the animated texts showed each "+N" and hid it at once, without the fade. There are five of them (`plus0`..`plus4`, `PLUS_SLOTS` in `index.js`), reused in turn, so up to five fade at once. Each is removed 1 s after it appears, and while it shows its row has `onclick="increment"` and the edge swipe, so a tap on a "+N" still counts. Checked in the Previewer: each "+N" shows at a random spot and fades, and the outline reads well on the cookie. Not yet checked on the watch: that the bound position is applied, and that five animations over the 466 px cookie do not bring back lost taps (before, one pill under the capsule was fine).

**Vignette:** right over the cookie, under the curved count and the "+N", is `vignette`, a full-screen `image` of `common/vignette.png` (`if="{{ !menu }}"`) that darkens the cookie towards the round edge, as in the clicker reference image, and leaves the centre clear. It is the same for every theme, so the theme textures are untouched. The PNG is 466x466 RGBA, all black, with alpha 0 up to 150 px from the centre, rising with a smoothstep to 215 (about 85 %) at 233 px; it is made by `tools/make_vignette.py` (pure Python, writes the PNG with `zlib`). Because it covers the whole screen it takes the cookie's taps, so it carries the same `onclick="increment"`, `onswipe="edgeSwipe"` and `ontouchstart="touchStart"` as `cookie-box`. It adds about 0.9 MB to the package (its raw `.bin`, see **Package size**). Risk: every fading "+N" now redraws two full-screen images with transparency, and full-screen images already cost lost taps once (below). Reported in October 2026 that the darkening looks right. Not yet confirmed: that taps anywhere count, the edge swipe opens the menu, the curved count and "+N" stay on top, and about 10 quick taps on the watch all count. If taps are lost, bake the same gradient into the ten `<id>.png` (466 px) instead and drop the layer: no cost on the watch and the same package size.

**Curved count:** the count and the line under it (a notice, else the frenzy, else the cookies per second) follow the round top edge with no background, as in the clicker reference image. Lite cannot rotate text (no `transform` outside `@keyframes`) and has no `svg`, and `canvas` rebooted the watch (see "Canvas reboots the watch" below), so each letter is its own `stack` in a `for`, positioned with a bound `style="left: {{ $item.x }}px; top: {{ $item.y }}px;"` and holding a dark copy 2 px down-right under the white (or gold) letter. The letters stay upright. `arcChars` in `index.js` centres the text on a circle around the screen centre (radius 215 px for the 38 px count, 177 px for the 30 px line; the Previewer draws a text a few px lower in its box than its centre, so the radii are tuned by eye to put the count against the top edge), with each letter's advance guessed from a per-character share of the font size (`charWidth`), since lite cannot measure text. The arrays start empty and are filled from `onInit` (through `setOwned` → `updateRates` → `updateArc`), and rebuilt only when the text changes. All letters sit in a 466x150 `arc` stack at the top with the cookie's tap and swipe handlers, so taps there still count. The count (`formatCount`) shows up to 9 digits with commas, then in thousands with K, M or B (`1,234,567K`), and past `999,999,999B` in scientific notation (`1.20e18`); other numbers (rate, prices, stats) keep the short `format` (`1.2M`). The commas are added with a `slice` loop: the first version used `replace(/\B(?=(\d{3})+$)/g, ',')`, which builds fine but makes the lite engine fail to evaluate the whole page (`Eval JS file failed`, `TypeError: wrong type of argument` in `previewer.log`, black screen), so avoid that kind of regex. The shop, upgrades and stats views show the same count text straight. Checked in the Previewer (October 2026) with `999,999,999K`, `1,253,648`, `0 / s` and a gold "Award: First cookie": evenly spaced, inside the round edge, taps on the letters count, the edge swipe still opens the menu and the menu hides the arc; the 12-character count also fits straight in the shop. Not yet checked on the watch: the same, and that rebuilding up to ~30 letter stacks every second does not cost taps.

The cookie does not change when tapped. It used to shrink for 120 ms by swapping the 466 px image for a 438 px one (two `if` images, since `class` cannot be bound), but that destroyed and recreated a full-screen image twice per tap, and on the GT 6 Pro (October 2026) quick taps were lost: only a few of several taps counted. Without the swap every tap counts. Do not bring back a press effect that recreates or resizes the cookie image; lite `@keyframes` are not a reliable way to scale an image either.

**Menu:** the edge swipe on the cookie view sets `menu`, which swaps the big cookie, the curved count, the "+N" and the golden cookie for a radial menu, as in the first watch of the concept art `WhatsApp Image 2026-10-25 at 1.57.09 PM.jpeg`: the theme's image at 170 px in the centre and six 100 px round buttons on a 155 px circle around it, clockwise from the top: shop (cart), stats, settings, close (X), awards (trophy), upgrades (up arrow). Each is an `if` image with fixed `left`/`top` in the `stack`, over a full-screen `menu-bg` div that only catches the edge swipe. The cart opens the shop, the up arrow the upgrades, the bars the stats, the trophy the awards, and the X closes the menu; the gear the settings. Another edge swipe, or a tap on the small cookie, closes the menu without counting a cookie. Opening the shop or the awards closes the menu, so Back returns to the big cookie. The golden cookie does not count down while the menu is open. The buttons are cut from the concept icon sheet (`3b371dd9-…png`, "Navegación principal" row, circles of radius 49 px at y=113) with a PowerShell `System.Drawing` script that scales each to 100 px bicubic and clips it to a circle, so the corners are transparent. Confirmed on the GT 6 Pro (October 2026): the sideways swipes that then opened and closed the menu worked, the small cookie closes it, the cart opens the shop and the trophy the awards.

**Shop view:** styled after the second watch of the concept art `WhatsApp Image 2026-10-25 at 12.18.38 PM.jpeg`: the count, the cookies per second and a gold "Shop" title at the top, then a `list` (340x260 px, ending about 50 px above the bottom so the last card is not cut by the round edge) of the `UPGRADES` in `index.js` (only those with `building: true`: Cursor, Grandma, Farm, Mine, +N per second). Each row carries `id`, its index in `UPGRADES`, and taps call `buy($item.id)`, because each view lists only some entries; `$item.id` in a handler works in lite. Each row is a dark card (`background-color` and `border-radius` on the `list-item`) with a 64 px icon, the name (24 px font), the gain and number owned (20 px), and a price pill with a small cookie: gold when affordable, grey when not (two `if` divs, as lite cannot bind `class`). There is no Back button: the edge swipe on the view returns to the cookie (the sideways swipe on the view div that came before it worked over the list too). The icons in `common/shop/` are 64 px squares cut from the concept icon sheet (`3b371dd9-…png`, "Íconos de edificios" row at y=330, and "+ Clics" for Tastier taps), with the sheet's near-black background (about RGB 14,13,10) turned transparent by a PowerShell script that ramps alpha from 0 to 255 over a colour distance of 14 to 40. `coin.png` is the pixel-art cookie at 24 px. Confirmed on the GT 6 Pro (October 2026): the icons, cards, 24 and 20 px fonts, gold pills when affordable, crown scrolling and the swipe back all work. The price is `base * 1.15^owned`. Tapping a row buys it; with not enough cookies nothing happens (the row is greyed out). `onclick="buy($idx)"` inside a `for` compiles to a handler that gets the row index. `items` is rebuilt as a new array on every change, because lite does not reliably notice changes inside array items.

**Upgrades view:** styled after the third watch in the top row of `WhatsApp Image 2026-10-25 at 12.18.38 PM.jpeg` and opened from the up-arrow button, which replaced the star. It is a copy of the shop view (same classes, header with a gold "Upgrades" title, `upgradeList` ref, edge swipe back) listing the `UPGRADES` with `building: false`. For now that is only "Tastier taps" (+1 per tap; it was "Golden finger" in the shop; it is still entry 0, so saves keep it). `refreshItems` fills both `items` and `upgradeItems`. The arrow button (`common/menu/upgrades.png`) was made from the up arrow of the "Mejoras" achievement category in the concept icon sheet (keyed by brightness, since a colour key left dark outlines from its tile) drawn on an empty button. The empty button was rebuilt from the six cut buttons: a first try took the darkest of the six per pixel and kept the icons' dark outlines as scribbles; what worked is the median colour per radius (the background is radial), each pixel taking the button colour closest to it, and a flat colour inside the icon area, where every button has its icon. Checked in the Previewer that the shop still buys the right entry. Confirmed on the GT 6 Pro (October 2026): the arrow opens the view, Tastier taps can be bought, and the shop lists only buildings.

**Stats view:** styled after the last watch in the top row of `WhatsApp Image 2026-10-25 at 12.18.38 PM.jpeg`, opened from the bars button in the menu. Same header and list size as the shop (count, cookies per second, a gold "Stats" title), then cards with a white label, a gold value and a 48 px icon on the right: cookies baked, cookies per second, taps, buildings (all upgrades that produce per second), tastier taps, golden cookies, awards ("N / 14") and time played ("5m 17s", or "1h 24m" past an hour). Time played counts the 1 s ticks, so it only grows while the app is open. The list is rebuilt every tick while the view is open, so the time and the counts stay live. The edge swipe returns to the cookie. The icons in `common/stats/` are cut from the concept icon sheet like the others (the clock is "Máquina del tiempo", the trophy is from the stats row). Confirmed on the GT 6 Pro (October 2026): it opens from the menu, the values are right, the time advances, the crown scrolls the list and the swipe returns to the cookie.

**Production and saving:** a 1 s `setInterval` adds the cookies per second. `@system.storage` holds `count`, `owned` (comma-separated counts in `UPGRADES` order, so new upgrades must be appended), `stats` (`baked,taps,golden,played`: cookies ever made, taps, golden cookies tapped, seconds the app has been open; older saves have fewer numbers and the missing ones read as 0) and `achieved` (one `0`/`1` per entry in `ACHIEVEMENTS` order, so append only). It saves 1 s after the last tap, every 10 s while producing, after each purchase and in `onDestroy`. `onInit` reads the keys in a chain and adds the stored values, so taps made before the reads finish are not lost. Nothing is saved until the whole chain has loaded, so a half-loaded state cannot overwrite the save. Large numbers show as 1.2K, 3.4M, and so on. Each save also stores `savedAt` (`Date.now()`).

**Offline earnings:** After the other keys are loaded (so the cookies per second are known), `onInit` reads `savedAt`, and adds cookies per second × seconds since `savedAt`, capped at 24 h. Because `savedAt` marks when `count` was saved, cookies produced after the last save are not counted twice. It then shows "+N away" in place of the rate. Messages there (offline earnings, achievements) are queued and show for 3 s each. Nothing is added if there is no `savedAt` yet, the clock went backwards, or nothing is produced. Confirmed on the GT 6 Pro (October 2026): reopening the app after a while adds cookies and shows the message, so `Date.now()` gives the real time there.

**Golden cookie:** the cookie view's `stack` also holds two `if` images, `golden-left` and `golden-right`, with fixed `left`/`top`. Only one exists at a time; there is one per side because lite cannot bind `class` and position binding is not proven. Every 45-120 s spent on the cookie view, one appears for 10 s over the left or right edge of the big cookie, level with the screen centre. Tapping it gives a frenzy: taps and production ×7 for 30 s, with "x7  N s" in place of the rate. Offline earnings do not include the frenzy. The positions assume a 466 px screen. Confirmed on the GT 6 Pro (October 2026), with the earlier 200 px cookie: it shows up in the right place, so `stack` with `left`/`top` works there, and the frenzy works. Confirmed on the GT 6 Pro (October 2026): the full-screen cookie, the capsule, the "+N" pill, the swipes and the golden cookie over the big one all work.

**Achievements:** `ACHIEVEMENTS` in `index.js` lists 14 (cookies baked, taps, first of each upgrade, cookies per second, golden cookies), each with a `value(state)`, a `goal` (done when the value reaches it), a category and an icon. They are checked whenever the count, the upgrades or the golden cookie count change, but only once the save is loaded, so saves made before achievements existed unlock everything they already qualify for at the next launch, without announcing old ones twice. A new one shows "Award: <name>". For those older saves, `baked` starts at the current count. Confirmed on the GT 6 Pro (October 2026): unlocking and the messages work.

**Awards views** (styled after the second and third watches of `WhatsApp Image 2026-10-25 at 1.57.09 PM.jpeg`, without their back buttons or page dots):

- The grid (`view: 'achievements'`) shows "Awards", "N / 14" and one tile per entry in `CATEGORIES` (Clicks, Cookies, Buildings, Speed, Golden) with icon, name and "done / total". It is a `list` of rows of three tiles, so it scrolls if categories are added. The rows use a nested `for`: `for="{{ (ri, row) in awardRows }}"` on the `list-item` and `for="{{ (ci, cat) in row.cats }}"` on the tile `div`, with `onclick="openCategory(cat.id)"`; naming the loop variables this way works in lite. Category names must fit a 104 px tile at 20 px ("Production" did not, hence "Speed").
- Tapping a tile opens that category (`view: 'category'`): its name, "done / total", and a list of cards with the achievement's icon, name, detail, a check (done) or a lock (not done), and, while a goal above 1 is not reached, a `<progress type="horizontal">` bar (gold `color`, `stroke-width: 8px`, brown `background-color`) with "value / goal".
- The edge swipe in a category goes back to the grid, and in the grid back to the cookie. Switching from the category to the grid inside the swipe handler left the grid tiles ignoring taps in the Previewer (from the menu they worked), so the swipe then switched in a `setTimeout(…, 0)`. The same happened once after the swipe back to the cookie (a menu button ignored the first tap after coming back from the awards), so `edgeSwipe` defers every view change the same way.
- The icons in `common/awards/` are 56 px squares cut from the concept icon sheet with the near-black background made transparent, like the shop icons; the buildings reuse `common/shop/`. `check.png` (36 px) is the gold "Comprado" circle, cut round; `lock.png` (36 px) is the "Bloqueado" lock with its grey tile (about RGB 26,26,25) made transparent.

Confirmed on the GT 6 Pro (October 2026): the grid, the category lists, checks, locks, progress bars, crown scrolling and both swipes back work.

**Crown:** every list (shop, awards grid, category) has a `ref`, and opening their view calls `this.$refs.<ref>.rotation({ focus: true })` 50 ms later, because the `if` view has to render before its list exists. With the focus, turning the crown scrolls the list. `rotation()` on `list` is in the lite typings since API 4. `setMonitorForCrownEvents()` (raw crown events for the page) was not used because it only exists since API 24, above our compatible SDK. Confirmed on the GT 6 Pro (October 2026): the crown scrolls both lists, and the shop keeps the focus although its items are rebuilt every second.

**Gestures:** the app has one gesture, a swipe from the left edge towards the centre. On the cookie it opens the menu, or closes it; in a category it goes back to the awards grid; in the theme list and the reset confirmation back to the settings; in the other views back to the cookie. Every element that used to take a swipe has `onswipe="edgeSwipe" ontouchstart="touchStart"`: `touchStart` keeps the event's `globalX`, and `edgeSwipe` only acts when `direction` is `right` (a swipe towards the centre) and the touch started within `EDGE_PX` (60 px) of the left edge. In lite the touch and swipe events have `type`, `target`, `currentTarget`, `timestamp` and the position straight on the event (`globalX`, `globalY`); there is no `touches` or `changedTouches`, so a first try that read `touches[0].globalX` never got a position and the gesture did nothing (checked in the Previewer, October 2026). Before, any sideways swipe (left or right, anywhere) opened the menu or went back. Checked in the Previewer (October 2026): the edge swipe opens and closes the menu and goes back in the other views, and swipes elsewhere do nothing. On the GT 6 Pro (October 2026) the watch also gives `globalX`, and a swipe started at the edge easily reads below 30, so 60 px leaves room; whether the whole gesture works on the watch with 60 px was not clearly confirmed (a first try seemed not to work, probably a stale install).

**Debugging in the Previewer:** `console.info` output shows only in DevEco's PreviewerLog panel, not in `%LOCALAPPDATA%\Huawei\DevEcoStudio6.1\log\previewer.log`; that file does log the Previewer's input (`TouchPress(x,y…)`, `Swipe received`). To see values without the panel, show them with `showNotice` in the cookie view's curved line under the count, a few short ones at a time, since long text runs off the round edge.

**Gestures and buttons on the watch** (checked on the GT 6 Pro, October 2026): swiping in any direction does nothing unless the app handles `swipe`. The system adds no swipe-back gesture to this app, so all four swipes are free to use. Confirmed on the GT 6 Pro (October 2026): `onswipe` on a `div` in the cookie view works (it was used to open the shop and the awards before the menu existed). Pressing the crown exits the app (system). The lower button does nothing in the app: it does not run its configured shortcut, and an `onkey` handler (set to vibrate) on the root `div` and the `stack` got no event, so the app cannot use it. Double-pressing it still opens Wallet (a system shortcut), even inside the app.

**Settings view:** styled after the second watch in the second row of `WhatsApp Image 2026-10-25 at 12.18.38 PM.jpeg` and opened from the gear. A "Settings" title (50 px from the top, so the first card clears the round edge) and a `list` of three static `list-item` cards: Theme with a 40 px picture of the current theme (see **Themes**), Language with the current language's name (a tap switches between English and Spanish), and a red "Reset game". The settings are stored apart from the game in the `settings` key (`language,theme`, e.g. `en,concha`; older saves had other settings first, `vibration,language,theme` and before that `sound,vibration,language`, so loading starts at the first field that is a language), load on their own at start, and survive a reset. There is no vibration: it was removed from the whole app (October 2026), with its setting, its icon and the `ohos.permission.VIBRATE` entry in `config.json`. It used `@system.vibrator` (`mode: 'short'` per tap, `'long'` for awards, failed purchases, the golden cookie, offline earnings and the reset), which worked on the watch and needed the permission with `reason` and `usedScene` (see `install-on-the-watch.md`). The icons in `common/settings/` are cut round from the "Íconos de ajustes" row of the concept icon sheet; the language globe was drawn with `System.Drawing` on that row's badge.

**Themes:** the Theme row opens `view: 'themes'`, a list of cards (shop card style) with a 64 px picture of each cookie, its name and the gold check on the current one. A tap picks it, saves the settings and returns to the settings; the edge swipe returns without changing it. `THEMES` in `index.js` lists ten, made from the user's pixel-art pastries (October 2026): A classic / Un clásico (jam roll, the default), A cookie / Una galleta, Everyday / Para diario (donut), Concha, Gingerbread / Jengibre, For the cold / Para el frío (cinnamon roll), Day of the Dead / Día de muertos (sugar skull), Kings' Day / Día de reyes (rosca), Christmas / Navidad (buñuelo) and Pan de muerto. The settings store the theme's `id`; an unknown or missing id falls back to the first theme. Each theme has two RGBA PNGs in `common/themes/`: `<id>.png` (466 px) for the big cookie, and `<id>_small.png` (170 px) for the menu centre, the theme list (64 px) and the settings row (40 px). The watch only scales them down, never up. Confirmed on the GT 6 Pro (October 2026): the 11.6 MB HAP installs and the cookies look sharp. The previous chocolate-chip cookie (`cookie.png`, `cookie_pressed.png`, `cookie_small.png`) was removed; `golden.png` and `shop/coin.png` still use it.

- The list passes the index in `THEMES` to `chooseTheme($item.id)`. Passing the string id (`'cookie'`) did nothing in the Previewer (no call, nothing in PreviewerLog); numbers work, as in the shop and the awards.
- The sources were 1254 px JPEGs with a fake transparency checkerboard (neutral greys about 205-255) baked in, including inside the donut, rosca and buñuelo holes. A pure-Python script (on raw RGB from `ffmpeg`) takes light neutral pixels (min channel ≥ 196, channel spread ≤ 10) and makes transparent every such region that touches the border, plus interior regions that look like the checkerboard (at least 25% of their pixels below 232; real holes have about 40-50%). A first try that treated every interior region above 600 px as a hole also erased white icing and sugar (gingerbread, cinnamon roll, sugar cookie), which have 0% dark pixels. One extra pass clears light grey JPEG fringe next to the background. Each cut-out is cropped square, scaled down to 1/12 (8.33%, 86-99 px, about the art's own pixel size) with `ffmpeg` `scale=flags=neighbor`, then scaled up with `flags=neighbor` to 466 and 170 px. The sources are pixel art drawn about 12x, although not on an exact grid (edge counts peak at a 12 px period on the concha, but the phase is unclear and JPEG blocks blur it). Tried before: the 1/12 image alone, scaled up by the watch, looked blurry; 1/6 of the source (172-199 px), also scaled up by the watch, did not look good either.
- **Package size:** the build stores every image twice: the source file and a raw `.bin` of 4 bytes per pixel plus a small header (`466x466` → 868,632 bytes). A `.jpg` is converted to the same raw `.bin`, so JPEG sources do not help. A first version with five pre-scaled images per theme (466, 438, 170, 64 and 40 px) made a 26 MB HAP; with one image per theme it was 1.8 MB at 1/12 and 3.3 MB at 1/6; with the current 466 and 170 px images it is 11.6 MB. Deleted images stay in `entry/build` and keep going into the package: after removing images, delete `entry/build` before building.
- **Scaling:** the Previewer scales a small `image` src up and down to the element's `width`/`height`, and upscaling keeps the pixels sharp there. The watch also scales it, but blurs it (smooth filtering), so a 95 px pixel-art cookie shown at 466 px looks blurry on the GT 6 Pro (October 2026). There is no way to choose the filter in lite: in the SDK's `ace-loader`, lite `image` only has the `src` attribute (`lib/templater/lite_component_map.js`), its styles are only `object-fit`, `match-text-direction` and `fit-original-size`, and nothing like `interpolation` or `image-rendering` exists (that is only in full ArkTS apps). So pixel art has to be stored already scaled with nearest neighbour to the size it is shown at.
- **Images built at runtime (tested on the GT 6 Pro, October 2026):** to ship only the 1/12 images and scale them in the app, a temporary view built a 120x120 nearest-neighbour test pattern in JS and wrote it with `@system.file` `writeArrayBuffer` (a `Uint8Array`) to `internal://app/` as 24-bit BMP, 32-bit BMP and RGBA PNG (zlib "stored" blocks, CRC32 and Adler-32 in JS), then set each as an `image` src. All three were written (43,254, 57,654 and 57,788 bytes). Only the **PNG** showed, and sharp; the BMPs drew nothing. But the watch's JS is slow: building the 120 px BMP took 1,356 ms and the PNG 3,900 ms (a few ms on a PC), so a 466 px PNG would take about a minute. The first run took about 10 s to show and then the watch froze and rebooted (likely out of memory); a second run took about 6 s and did not. In the Previewer the write fails with code 301 ("File or directory doesn't exist"), since it has no app storage, so this can only be tried on the watch.
- **Canvas reboots the watch (GT 6 Pro, October 2026):** a temporary view drew the 1/12 concha (94 px, quantised to 16 colours, 3,480 rects decoded from a 17 KB string) with `fillRect` on a full-screen 466 px `canvas` in a `stack`, 50 ms after the view opened. In the Previewer it drew sharp in 78 ms. On the watch, opening the view rebooted the watch at once, so it is not known whether the canvas itself, its size or the number of `fillRect` calls is the cause. Not narrowed down, since every try reboots the watch.
- **No other way to draw pixel art at runtime:** lite has no `svg` component (the components in `lib/templater/lite_component_map.js` are `div`, `stack`, `list`, `swiper`, `tabs`, `text`, `marquee`, `image`, `image-animator`, `analog-clock`, `input`, `switch`, `slider`, `picker-view`, `progress`, `chart`, `qrcode` and `canvas`, plus `camera` and `video` on smart vision only; `svg` is only in the full JS profile), no `box-shadow`, and thousands of `div`s would mean thousands of components. So the cookies stay pre-scaled PNGs.
- **SVG does not work:** an `.svg` src is packaged as-is (no `.bin`), and the Previewer draws nothing for it, not even a two-rect SVG. A 94x94 pixel-art cookie as SVG rects was also 377 KB (6,632 rects, since the JPEG noise leaves many colours).

Checked in the Previewer: the default theme on the big cookie and in the menu, the theme list, choosing a theme (big cookie, menu cookie and settings picture change), and scrolling the list.

**Reset confirmation:** "Reset game" opens `view: 'confirmReset'`: the reset icon, "Reset game?", "All progress will be lost", and Cancel (grey) and Reset (red) buttons. Cancel or the edge swipe returns to the settings. Reset zeroes the count, upgrades, stats, play time and achievements, clears the notices, frenzy and golden cookie, saves and returns to the cookie.

**Languages:** every text the player sees is in `TEXTS.en` / `TEXTS.es` in `index.js`, and names in `UPGRADES`, `CATEGORIES` and `ACHIEVEMENTS` are `{ en, es }` objects. The page binds `{{ t.<key> }}`, where `t` is the current language's table. `setLanguage` swaps `t` and rebuilds the lists that hold translated names. English is the default. Spanish names were chosen to fit the same widths as the English ones ("Tastier taps" is "Mejor toque", since longer names do not fit the 164 px name column at 24 px). Renaming an upgrade or achievement is safe, because saves store them by position, not by name.

**Tap sound: not possible (tested on the GT 6 Pro, October 2026), so the app has no sound and no Sound setting.** The Lite Wearable SDK has no audio API (no `@system.audio` typings, and no multimedia capability in `device-define/liteWearable.json`). `import audio from '@system.audio'` still compiles, to `requireModule('@system.audio')`; the Previewer has no such module (the import is just empty, the page still loads). On the watch the module exists and looks like the Quick App `@system.audio` ([watch docs](https://watchdoc.quickapp.cn/api/system/audio.html)): own properties `play`, `pause`, `stop`, `getPlayState`, `src`, `currentTime`, `duration`, `autoplay`, `loop`, `volume`, `muted` and the `on<event>` handlers. `src` is an accessor (getter and setter); `loop = true` sticks. `getPlayState` returns `{"state":"stop","currentTime":-1,"autoplay":false,"loop":false,"volume":0.5,"muted":false,"src":""}`. Nothing tried makes it play: every value given to `src` is dropped (it reads back empty, `duration` is NaN), and `play()` then fires `onerror` with no argument:

- Paths: `/common/…` and `common/…` (files in the package), `internal://app/…` (written first with `@system.file` `writeArrayBuffer`, which works there), and an `https://` URL. `internal://cache/`, `internal://files/` and `internal://tmp/` cannot be written ("202 Invalid parameter").
- Formats: MP3, AAC (ADTS), OGG/Opus, AMR-NB, WAV 16-bit and 8-bit (made with ffmpeg; the bytes were checked against the files after the base64 round trip).
- Calls: `src` then `play()`, `play({ uri })`, `play({ src })` (these never run `success`, `fail` or `complete`), with `volume = 1`, `muted = false`, `streamType = 'music'`.
- Permissions: adding `ohos.permission.READ_MEDIA` and `ohos.permission.MODIFY_AUDIO_SETTINGS` to `reqPermissions` (same form as VIBRATE) still installs, and changes nothing.

So a third-party app cannot set what the player plays; the module seems to be there for system apps. Do not try again without a new SDK or documentation that shows a different API. The official Chinese documentation (October 2026) agrees: on developer.huawei.com the JS reference has pages for modules such as `@system.vibrator` (`/consumer/cn/doc/harmonyos-references/js-apis-system-vibrate`), but `js-apis-system-audio` is a 404, and searching the Chinese docs for `system.audio` finds nothing. The only Lite Wearable sound path the docs and Chinese forums mention is a phone app sending a notification to the watch through Wear Engine (the watch then rings or vibrates by its own settings), which needs a phone app and is too slow for a tap sound. Two traps met on the way: `requireModule()` of a module that is not there, or of `@system.app` or the already-loaded `@system.audio`, throws in a way that `try`/`catch` does not reliably stop (on the watch a probe just stopped silently), so do not probe modules by name; and `file.list` on `internal://app/` never called back. These tests ran from a temporary full-screen view (Settings > Experimental) that showed the results line by line.

Checked in the Previewer: switching to Spanish (shop, awards, stats, settings, confirmation), and cancelling and confirming a reset. Confirmed on the GT 6 Pro (October 2026): the settings view looks right (it then also had a Vibration switch, which silenced the taps). Language and reset not yet reported from the watch.

The big cookie images are 466x466 opaque RGB PNGs on black (see **Themes**). The watch handles 466 px images fine (GT 6 Pro, October 2026). `golden.png` is a 90x90 RGBA PNG with a transparent background: the same pixel-art cookie, scaled bicubic and tinted gold with a `ColorMatrix` (luminance × 2.0 / 1.4 / 0.4 for R / G / B). An opaque PNG showed as a black square over the big cookie, so the round shape comes from the alpha channel (`border-radius` on the image was not tried). Confirmed on the GT 6 Pro (October 2026): the `image` component honours PNG transparency, so the golden cookie shows round.

Confirmed on the GT 6 Pro (October 2026): the cookie press, the "+1" rising and fading (so lite keyframes do apply `translateY` and `opacity`), the vibration on each tap (since removed), and the count surviving closing and reopening the app. The shop (scrolling list, buying, greyed-out rows), the production timer and saving `owned` also work on the watch.

The name on the watch is `MainAbility_label` in `entry/src/main/resources/base/element/string.json` ("Bakery Clicker"); the template's default is "label". The launcher icon is `resources/base/media/icon.png` (104x104) and `icon_small.png` (92x92), RGBA PNGs; the template's default is a blue square with four white squares. Our icon is a drawn cookie with a chocolate drizzle and a play triangle: the source (1254 px WebP on white) was decoded with `ffmpeg` to raw RGB, a pure-Python script (Pillow is not installed on this PC) flood-filled the white background from the borders (min channel above 225) to transparent and cropped to the cookie, and `ffmpeg` scaled it with `premultiply,scale=flags=area,unpremultiply` so the edge has no white halo.

## Previewer

Open `index.hml` and click **Previewer** on the right edge. It builds (`buildPreviewerResource`, a few seconds) and shows a round LiteWearable watch. Clicks on the screen act as taps. To fake the edge swipe with computer use, press at the edge, wait about 0.3 s and make the first moves small: a quick drag makes lite's `touchstart` report a position already far from the edge, so `edgeSwipe` ignores it.

- Clicks less than about a second apart counted once (three quick clicks → 1). Clicks two seconds apart each counted. Not yet checked whether a real watch behaves the same.
- The default text size (38px) looks small on the round screen. Lite Wearable only accepts some font sizes; try larger ones in the Previewer before changing it.
