# Compare ways of drawing on the watch

Goal: find out which way of drawing works on the GT 6 Pro and which is fastest: `canvas`, plain components (`div`s placed with a bound `style`), or other lite components.

**Warning: do not run tests that reboot the watch over and over.** After several reboots in a row (October 2026) the GT 6 Pro showed a message that it would reset to factory settings in a few seconds; the watch then had to be paired with the Android phone again and the app reinstalled. The tests had been run one right after another, reopening the app as soon as the watch was back on, so the likely trigger is several reboots in a short time (many devices take that as a boot failure and offer a reset); not confirmed. The tests that rebooted it are out of the lab (see **Removed tests**). Run a new crash test once, not again to get a screenshot, and after a reboot wait a few minutes before the next one.

**What "reboot" means here:** when the app goes over the limits, the screen goes black for about 10 s, ignores buttons and gestures, and then the watch face comes back. The Huawei logo does not show, as it does when the watch is restarted by hand, so it is not a full boot: the system most likely kills the stuck app and restarts its UI. The app's last `storage` writes are lost with it. "Turned the watch off" below is the same thing.

## Conclusions

- **Canvas is the fastest way to draw shapes**, about 10 times faster than `div`s (100 squares: 54 ms against 544 ms on the watch), but **only up to about 1,100 `fillRect` per canvas element**. Each `fillRect` costs about 0.34 ms. 1,000 in one go worked (half a second); 1,500, 2,000, 2,500 and 3,500 rebooted the watch. Drawing in parts of 250 with a 0 ms timeout between them does not help: 3,500 in parts rebooted it before a quarter (under ~875 rects), the 4-colour concha in parts at about half (~980 of 1,962), the 8-colour one before half (under ~1,360 of 2,724). So the limit is the number of rects drawn on one canvas, not how long JS blocks; the canvas seems to keep every draw call (the Previewer keeps what each part drew). Lite `canvas` likely stores the calls and replays them, so memory grows with each one.
- So **pixel art stays as pre-scaled PNG images**: the 94x94 concha needs 1,962 rects even with 4 colours. The earlier full-screen concha reboot (3,480 rects) was this limit.
- **The limit is about 1,100 `fillRect` in total, however slowly they are drawn.** With the screen kept on, one square per 16 ms step went black at 1,104 (37 s) and one per 250 ms at 1,114 (more than 4 minutes); 10 squares per step also stopped at about 1,100. Updating the screen is not the problem: the text-only loop changed the text 5,000 times, every 16 ms, and finished. So whatever piles up comes from canvas draw calls, not from frames, text, timers or time. It is not a JS memory leak or recursion: in the Previewer, which has the same 512 KB JS heap and logs running out of it, e1 went past 1,500 steps with no error.
- **The screen timeout looks like a crash.** The watch turns the screen off after about 10-15 s without input, and the app closes. Earlier counting runs that ended at 350-512 steps (e1-e7 at 30 steps a second, about 12 s) were this, not a limit; the lab now keeps the screen on (see **The lab**).
- **A new canvas starts the count again.** e2 removes the canvas (`if` off) and makes a new one every 100 squares; with the screen kept on it drew 5,000 squares in 50 canvases and finished. So the limit is about 1,100 `fillRect` per canvas element, and anything that draws for long has to replace its canvas well before that (for example every few hundred rects). The new canvas starts empty, so whatever should stay on screen has to be drawn again on it, and the swap in e2 takes two `CANVAS_WAIT_MS` (50 ms) waits, a visible blank. s1 and s2 test hiding that: a frame is a black background and 39 wall-like columns (40 rects), and every 20 frames (800 rects) the drawing moves to a fresh canvas. s1 has two canvases on top of each other (`cvA`, `cvB`, each with its own `if` and `show`): the next frame is drawn on the hidden one, the two swap `show`, and the old one is remade while hidden. s2 remakes a single canvas in place, waiting `CANVAS_WAIT_MS` (50 ms) after removing it and again after adding it back; s3 does the same with 0 ms waits. All three run in the Previewer (600 frames; s3 at 29 ms/frame). On the GT 6 Pro: **s1 crashed**, and so did **s3**. Likely two full-screen canvases alive at once are too much native memory (each 466 x 466 x 4 bytes, about 870 KB): s1 keeps two, and s3 adds the new canvas before the old one is gone. **s2 finished 600 frames at 54-55 ms/frame** (about 18 fps), but every remake freezes the screen for **575 ms** (the longest gap between two frames), a visible hitch every 20 frames. So the swap works but costs about half a second each time, which rules out smooth long animations at 40 rects a frame. **Drawing only what changed** (`deltaWalls`): the canvas keeps what was drawn, so each column remembers its height and only the top and bottom bands that grew (in its colour) or shrank (in black) are drawn, 2 rects per changed column; the canvas is remade at 900 rects and redrawn in full. Counted in Node for 600 frames: walls that move all the time (8 px steps) cost about 54 rects a frame, more than redrawing everything (40), since nearly every column changes every frame, so that variant was dropped. Walls that jump to a new view every 15 frames and stay still in between (d2, "Delta, steps", like stepping through a maze) cost about 5.5 rects a frame and need a new canvas only 3 times in 600 frames, so the half-second hitch comes every 7 s or so instead of every second. d2 runs in the Previewer; not run on the watch yet.
- **Lite canvas has no `clearRect`** (a test that called it got `TypeError` on the first frame in the Previewer), so a canvas cannot be emptied without remaking it. The lite simulator (`hms/previewer/liteWearable/bin/Simulator.exe`) has the names `fillRect`, `strokeRect`, `fillText`, `arc`, `beginPath`, `closePath`, `moveTo`, `lineTo`, `stroke`, `fillStyle`, `strokeStyle`, `lineWidth`, `font`, `textAlign`, but not `clearRect`, `strokeText`, `drawImage`, `putImageData`, `getImageData` or `setLineDash`.
- **`div`s are limited by the 512 KB JS heap**: each item bound in `data` costs about 1 KB. 100 work (slowly); 400 and 1,000 turned the watch off; rebuilding 100 `div`s 30 times also rebooted it.
- **Small animations run at about 33 ms/frame (30 fps)** with a canvas, a `div` or the `progress` arc; swapping an `image` src is slower (51 ms/frame).
- **`image-animator`** plays a list of images by itself. **`@keyframes` `rotate`** turns an image in place, if the image sits at 0,0 inside a positioned `stack` (on the image itself, the animation drops its `left`/`top` and it turns in the top-left corner); only fixed angles or full turns, since `transform` is only allowed inside `@keyframes`. **`progress type="arc"`**, **`chart`** and **`qrcode`** work. **`analog-clock`** draws nothing, in the Previewer or on the watch: the build accepts it (it is in `lite_component_map.js`), but the lite engine does not have it. When the view opens, `previewer.log` says twice `[ACELite][ERROR]:Fail to create element because the tag is not supported.` (once for `analog-clock`, once for `clock-hand`), and not even the clock's own `background-color` shows. It is not the black background or the hand image: a grey clock with a thin white hand (`common/lab/hand.png`) also showed nothing.

Lite Wearable components (from `lib/templater/lite_component_map.js`): `div`, `stack`, `list`/`list-item`, `swiper`, `tabs`, `text`, `marquee`, `image`, `image-animator`, `analog-clock`/`clock-hand`, `progress`, `chart`, `qrcode`, `input`, `slider`, `switch`, `picker-view` and `canvas`. No `svg`.

## The lab

The branch `lab-dibujo` turns the app into a list of tests ("Drawing lab"); its last row, "Back to the game", opens the game with `router.replace`. The lab is temporary and stays off `main`.

- **The lab has to be `pages/index/index`.** A first try added it as `pages/lab/lab`, first in `config.json` `pages`; the HAP contained it, but the watch still opened the game. The app starts at `pages/index/index` whatever the order, so on the branch the lab is `pages/index/` and the game moved to `pages/game/game.*`.
- Tap a row to run it. Tap anywhere to go back to the list. Each row shows its last result under its name.
- Before a test starts its id is saved as `labRunning` (on the `storage.set` success callback) and cleared when it finishes; the next launch shows a test that did not finish as `CRASH / reboot`. Results are saved as `labResults` (`id=text|id=text`, no JSON). But when the watch turns off, the last `storage` writes are often lost (rows show `-` again and the marker can be gone), so write down crashes by hand. The Previewer forgets storage when it reloads.
- `js N ms`: time spent in the drawing calls. `all N ms`: until a 0 ms `setTimeout` runs after them. `N ms/frame`: average over 60 frames asked for every 16 ms (`FRAME_MS`), so 16 is full speed and more means drawing falls behind. A first version chained frames with 0 ms timeouts: the Previewer ran all 60 before drawing any and reported 0 ms/frame.
- Rows pass their index to `run`, since the Previewer ignores string arguments from `onclick`.
- **Keep the screen on:** the watch turns the screen off after a few seconds without input, and the app closes, which looks just like a crash. The lab calls `brightness.setKeepScreenOn({ keepScreenOn: true })` (`@system.brightness`, no permission declared) in `onInit`; if it fails, the list title says "Screen-on failed". It works on the GT 6 Pro: tests ran for minutes without touching the watch. Do not tap during a test: a tap goes back to the list.
- `for` and `if` cannot be on the same element (build error at that line); the `div` grid is a `for` inside an `if` `stack`.
- Values the page keeps outside `data` (`results`, `timer`) are module variables, as in the game. As non-function properties of the page object they did not reach `this`, and the list stayed empty in the Previewer.
- The build warns that `pivot-x`, `pivot-y` (`clock-hand`) and `total-width` (`progress`) are not standard; it still builds.
- Previewer quirks: the first tap after scrolling the list is often ignored, and a long fast drag does not scroll it (shorter drags do). It also stopped picking up edits made outside DevEco after `sed -i` left a temporary `sedXXXXXX` file in its copy (`entry/.preview/.../pages/index/`); reloading did not help. Deleting `entry/.preview` (generated), stopping the Previewer (red square), opening it again and clicking Reload rebuilt it. Edit files with the editor tools rather than `sed -i` while the Previewer is open.

**Cookie as rects:** `tools/make_concha_rects.js` (run with DevEco's `tools/node/node.exe`, no packages) reads a 466 px theme PNG, finds its art grid (94x94 for the concha) by trying which nearest-neighbour upscale matches best, reduces the colours with median cut and writes a module `{ size, colours, count, rects }`, where `rects` is a string of five characters per rect (x, y, width, height, colour index, each `String.fromCharCode(48 + value)`), so the page decodes it without building objects. Usage: `node tools/make_concha_rects.js <png> <out.js> <colours> <pixels|runs|rects|layered>`. The concha has 6,739 opaque pixels and the JPEG noise leaves short runs, so merging barely helps: 16 colours, 3,938 runs or 3,478 merged rectangles; 8 colours, 2,724 rectangles; 4 colours, 1,962 with `layered` (each row first drawn as one run of the main colour, the other colours over it). In the Previewer both concha versions looked right (8 colours keeps the orange crust, 4 makes it dark brown). All are over the ~1,000-rect limit.
